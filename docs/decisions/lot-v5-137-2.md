# Lot v5.137.2 — Une vidéo survit au démarrage (A768)

**Origine.** Retour de l'auteur, juste après la v5.137.1 : « maintenant les vidéos qui étaient sur mon ordi (là où
j'ai ajouté le protocole avec les vidéos) ne s'affichent pas, sous prétexte qu'elles ne sont pas synchronisées ».
Reproduit par une sonde qui rejoue son parcours sur la même base locale, v5.137.0 puis v5.137.1, serveur simulé :
import Notion avec vidéo dans Perso, synchro, déplacement dans une bibliothèque, synchro, **relance** — la vidéo
disparaît de l'appareil au relancement, et sa copie de bibliothèque est mise en file de suppression.

## A768 — Les ménages qui effacent comptent les vidéos ; une suppression distante se revérifie ; récupération

*Corrige A757 (les vidéos) et complète A767.*

**Le défaut.** Trois ménages effacent des binaires de l'appareil, et deux ne lisaient que `docs` :
- `gcAttachments`, **à chaque démarrage** (`load`) : toute vidéo y passait pour orpheline — effacée de l'appareil, et
  son chemin distant mis en file de suppression (`ac-att-del`), rejouée par la synchro suivante (le téléphone, éditeur
  ou administrateur, pouvait ainsi supprimer la copie de bibliothèque qu'il venait de recevoir) ;
- `purgeDraftAtts`, à l'abandon d'un brouillon neuf ;
- `_syncAttachments` comptait bien les vidéos (A757), mais une lecture des protocoles en échec valait « aucun
  protocole » (`.catch(()=>[])`) — toutes leurs pièces auraient été purgées.
Aucun témoin ne **relançait** l'app : les vidéos vivaient tant que la page restait ouverte, et chaque mise à jour, qui
recharge l'app, les effaçait.

**La correction.**
1. **Une seule lecture de « ce qui est cité »** (`attCiteIds`, PURE) : documents ET vidéos de chaque élément (tombes
   comprises, restaurables), et tout id qu'une ligne du texte nomme (`](att:ID` ou `](vid:ID)`). `gcAttachments` et
   `purgeDraftAtts` la lisent ; `_syncAttachments` ne purge pas non plus un binaire qu'un texte nomme.
2. **Une suppression distante se revérifie au moment de partir** (`attDelSur`, PURE) : un chemin de la file ne part que
   si aucun élément VIVANT ne cite son fichier dans l'espace de ce chemin ; sinon il sort de la file sans rien
   supprimer. L'ancien chemin d'un déplacement reste supprimable (l'espace qui cite est l'autre). La file n'est
   rejouée qu'après une lecture complète des éléments.
3. **Une lecture des protocoles qui échoue n'efface plus rien** ce passage-ci.
4. **Récupération** : un fichier cité dans une bibliothèque où je peux écrire, introuvable à tous ses chemins, est
   aussi cherché dans MON Perso du serveur — là où il était parti avant le déplacement de son élément (A767), et où le
   ménage fautif ne l'a pas supprimé (il visait le chemin relabellisé). Retrouvé : remis à l'espace qui le cite
   (`scope`, `dirty`), il y repart à la synchro suivante, l'ancien chemin est ensuite retiré ; c'est dit (« ↻ n
   fichiers retrouvés dans votre espace Perso du serveur »).

**Ce qui ne revient pas.** Une vidéo qui n'était plus ni sur un appareil, ni sur le serveur (jamais envoyée, ou sa
copie déjà supprimée par la file) ne peut pas être reconstituée : la réimporter depuis son fichier d'origine.

**Témoins.** `tests.html` A768 : `attCiteIds` (documents, vidéos, tombes, texte), `attDelSur` (même espace cité →
gardé ; ancien chemin d'un déplacement → supprimable ; tombe seule → supprimable). `audit-doctrine` « A768 », serveur
simulé avec ses lignes (la réconciliation au relancement en dépend) et **un vrai relancement** (`page.reload`) : la
vidéo reste et rien n'est supprimé ; une file empoisonnée ne supprime rien et se vide ; une vidéo restée dans le Perso
du serveur est retrouvée, remise à la bibliothèque, y repart, le Perso nettoyé ; l'abandon d'un brouillon ne l'efface
pas. Vérifié capable d'échouer : les quatre correctifs neutralisés → quatre rouges.

*Formes écartées.* Retirer les ménages (ils rattrapent tout chemin d'abandon : sans eux, l'appareil se remplit de
binaires orphelins) ; n'ajouter que `videos` dans chaque ménage (la leçon est que trois listes de références avaient
divergé : une seule fonction les lit désormais) ; vider d'office la file de suppression (elle porte aussi les
suppressions légitimes : anciens chemins d'un déplacement, fichiers vraiment abandonnés).
