# Lot v5.126.3 — Dans un PDF, le surlignage suit le zoom sans attendre le rendu (A743)

**Origine.** Après la v5.126.2 (A742), l'auteur signale : « le surlignage ne revient pas après zoom ». Correctif ;
aucun changement de modèle ni de serveur. Complète A742, amende A554 sur un point.

## A743 — Les calques d'une page PDF se reposent à la nouvelle échelle dès le zoom

**Ce qu'A742 couvrait.** Le zoom revenu à une échelle DÉJÀ rendue (aucun nouveau rendu, donc rien ne reposait les
calques). Rejoué sur Chromium, tous les chemins de zoom reposent le surlignage : boutons, Ctrl + molette, pincer,
redimensionnement de la fenêtre.

**Ce qui restait.** Depuis A554, un zoom retire les calques posés au pixel (surlignage, liens) et attend le NOUVEAU
canevas pour les reposer. Deux cas les laissaient absents :
- un rendu **lent** (gros document, téléphone) : absents tout le temps du rendu ;
- un rendu qui **échoue** : à fort zoom, le canevas dépasse ce qu'iOS accorde ; l'erreur est avalée par
  `renderPdfPage`, l'ancien canevas reste étiré, et les calques ne reviennent jamais.

**Remplacé en v5.126.4 (A744)** : les calques sont désormais en pourcentage de la page, plus rien ne les repose.

**Décision (d'alors).** La place d'un calque ne dépend que de l'échelle (`_pv.cssW`) et de la page (`s.vp`), pas du canevas.
`pdfApplyScale` les repose donc aussitôt, sur le canevas étiré, pour toute page déjà rendue une fois ; le nouveau
rendu, quand il aboutit, les repose comme avant.

**Limite dite.** Reproduit en faisant échouer le rendu sur Chromium ; WebKit (iPhone) n'est pas jouable dans le
conteneur de la session, la CI rejoue les tests unitaires sur WebKit mais pas ce harnais. Si le défaut persiste sur
l'appareil, vérifier d'abord la version affichée (le service worker sert l'ancienne jusqu'à sa mise à jour).

**Garde-fou.** `audit-pdfsearch`, « zoom dont le rendu échoue : le surlignage suit l'échelle quand même » — dit alors « vérifié
capable d'échouer » : preuve FAUSSE, cf. le rectificatif du lot v5.126.5 (A745).
