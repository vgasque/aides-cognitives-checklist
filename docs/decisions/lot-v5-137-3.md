# Lot v5.137.3 — La carte des images se tient par chemin (A769)

**Origine.** Retour de l'auteur, après la v5.137.2 : le bandeau « Envoi de vos données — 2 / 17 images · 0 / 1 Mo »
revient « en boucle à chaque synchronisation ». Les requêtes de contrôle passées par l'auteur sur le stockage : aucune
vidéo sur le serveur (elles ne l'avaient jamais atteint, A768), aucun fichier orphelin.

## A769 — Une image, un espace, un fichier ; une image refusée ne se renvoie pas de la session

*Corrige A766.*

**Les défauts.**
1. **Le va-et-vient.** La carte de ce qui est déjà en fichier (`ac-img-up`) avait pour clé l'**id** de l'image, alors
   que le chemin du fichier dépend de l'**espace** de l'élément (`u/<compte>/…` ou `l/<bibliothèque>/…`). Une même image
   citée par deux éléments de deux espaces — « Copier dans Perso » d'un protocole de bibliothèque, un Markdown collé
   d'un autre protocole (A729), qui gardent l'id — se voulait à deux chemins sous une seule entrée : chaque synchro la
   renvoyait à l'un et mettait l'autre en file de suppression, sans fin. Les lignes de l'élément « perdant » gardaient
   leur image en base64.
2. **La boucle d'un refus.** Une image refusée par le serveur (schéma non rejoué : le stockage n'accepte pas encore les
   images ; quota) n'entrait pas dans la carte et repartait à CHAQUE synchro, bandeau compris ; la notification ne se
   disait qu'une fois par ouverture.
3. **Le message d'une vidéo absente** (A767) disait « ouvrez l'app sur l'appareil qui l'a ajoutée : elle l'enverra » —
   faux sur cet appareil-là, quand le ménage d'avant A768 l'en avait effacée.

**La correction.**
1. **La carte a pour clé le CHEMIN** (`imgCarteNorm`, PURE) : une carte d'avant (clé = id) est relue sous ses chemins.
   `imgStrip` cherche l'image au chemin de SON élément ; `_syncImages` envoie une fois par chemin, et le ménage retire un
   chemin qu'aucun élément ne cite plus (l'ancien chemin d'un élément déplacé part ici, une fois le nouveau envoyé) ;
   `imgHydrate` inscrit le chemin d'où l'image est venue.
2. **Une image refusée ne se renvoie pas de toute la session** (`Sync._imgRefus`, par chemin) ; l'envoi reprend à
   l'ouverture suivante — le temps de rejouer `supabase/schema.sql`.
3. **La garde des suppressions voit aussi les images** (galerie et attente, `gardes` passé à `attDelSur`) ; `refs` reste
   aux binaires de l'appareil, parce qu'il décide aussi des téléchargements.
4. Le message dit : « △ Vidéo introuvable, ni sur cet appareil ni sur le serveur. Si un autre de vos appareils l'a
   encore, ouvrez-y l'app : elle l'enverra. Sinon, réimportez-la depuis son fichier d'origine. »

**Témoins.** `tests.html` A769 : `imgCarteNorm` (relecture d'une carte d'avant, entrées invalides écartées), une même
image confirmée dans deux espaces s'allège dans les deux éléments ; les témoins A766 d'`imgStrip` passent par la carte
relue. `audit-doctrine` A767 suit le nouveau message.

*Forme écartée.* Donner un id neuf à l'image copiée dans un autre espace (comme les documents, A689) : le collage d'un
Markdown (A729) et les copies existantes gardent l'id, et la carte par chemin règle le cas sans réécrire aucun élément.
